## Scope and invariants

Both clients must read and mutate the same account, viewing, library, relationship, recommendation, and conversation records through the existing Express API. Shared behavior includes privacy, source attribution, consent, retries, filtering, and pagination. Navigation and controls remain appropriate to React/browser and SwiftUI/iPhone. The existing film catalog is the scope; TV identity, push delivery, production deployment, and a new visual brand are not added by this alignment.

The current baseline is `ios/FEATURES.md`, the implemented native features, and `docs/RECOMMENDATION_LIFECYCLE.md`. An existing dirty worktree is preserved. Earlier native test results are historical evidence, not proof of web parity.

## Architecture decisions

1. Keep one modular Express application and one data store. There is no mobile-specific backend or web copy of lifecycle logic. Authorization and viewer-specific projections remain server-owned.
2. Treat OpenAPI 3.1.1 as the portable wire contract. Generate TypeScript declarations using the development-only [openapi-typescript](https://openapi-ts.dev/introduction) tool; keep Axios session transport and Swift Codable. Generated types add no browser runtime. Server tests must verify actual payloads, since type generation alone does not validate runtime responses.
3. Fetch a bounded page when a destination opens. Filters belong on the server before pagination. A page continuation is explicit; a screen must not silently download every page to compute global counts. Use API summaries for summaries.
4. Scope client state to account and resource/query identity. Ignore stale responses after navigation, filter changes, or sign-out. Failed writes preserve the person's input; revoked access clears restricted content. Private drafts stay local and account-scoped.
5. Treat writes and subsequent refreshes as separate outcomes. A successful viewing save remains successful when a recommendation or library refresh fails. Preserve stable request IDs for identical retries.
6. Keep stateful components near their route and reusable domain controls in feature folders. Reuse semantic styling and accessibility behavior, not a shared cross-platform renderer.

### Local drafts and read contracts

- Web drafts use the browser's [IndexedDB API](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB). No storage runtime library was added. One versioned record per account retains film, edit target, date, privacy, note, feelings, enjoyment, highlights, photo, attribution, and create-request UUID. Records are validated when reopened. A read/write transaction checks the observed revision before replacing or deleting it, preventing another tab's newer draft from being silently overwritten.
- Autosave is debounced by 350 ms and flushed when the page becomes hidden or the composer unmounts. Save and Keep draft await the storage transaction. A pending unsaved change requests the browser's normal leave-page confirmation. Browser shutdown or site-data removal can still lose local data; this is not server synchronization. Draft recovery stays available when a newly requested film cannot load. Unreadable versions require an explicit discard. Account deletion now removes the owner draft after the server confirms deletion, with a separate retry receipt when local cleanup fails.
- Create retries use the persisted UUID and payload. An altered payload after an ambiguous committed write remains a server 409, directing the person to Diary instead of silently creating a second viewing. Edits send only editable fields. A committed response remains successful if draft cleanup or subsequent discovery fails; each has its own recovery action.
- [Library and shared-viewing OpenAPI](api/library.openapi.json) documents owner summaries, saved-film paging/search, bounded film status, and shared-film comparisons. Type generation covers saved-film, summary, status, and comparison shapes. [Recommendation OpenAPI](api/suggestions.openapi.json) continues to cover the lifecycle. `contracts:generate` and `contracts:check` cover those files and the social/safety contract added in the third slice.
- The web global provider loads only an authoritative summary and a 12-film saved preview. Diary, saved-film history, and shared-film comparisons each load one page on opening. A preview cannot determine saved/watched state elsewhere: `/api/library/status` checks only films already loaded by the screen, in batches of at most 100 IDs. Switching accounts replaces the provider and its authenticated consumers before they render the next account. Signup/recovery live outside this boundary so their one-time recovery-code receipts stay mounted when authentication changes.
- Shared comparisons select the latest owner viewing and the other person's latest visible public viewing for each shared film. Owner-private words are returned only to that authenticated owner. Search, visibility, blocking, and moderation rules apply before pagination. Offset pages can shift after writes; clients refresh on mutations and deduplicate appended IDs. They are not snapshot-isolated exports.

### Storage and growth boundary

AWS is the backend deployment target, confirmed September 25. [ADR 0001](adr/0001-platform-data-and-ai-boundaries.md) records the researched language/data choice and model-independent AI boundary. The user will share available AWS resources and scope deployment separately. No AWS service selection, infrastructure provisioning, credential setup, or deployment is authorized by this alignment work. Preserve one shared HTTP contract and replace the local database adapter behind `DatabaseClient`; keep account/session policy server-owned and catalog/recommendation work behind their existing service boundaries. Media storage and asynchronous jobs need explicit interfaces when those integrations are scoped, rather than embedding provider calls in SwiftUI or React. Choose the AWS database, compute, object storage, secrets, and job services against the actual requirements and available resources later. AWS readiness is not claimed by the current local checks.

The current PGlite adapter is a single-process persistent store with an exclusive filesystem lock. It is not a horizontally scalable deployment. Its PostgreSQL SQL and `DatabaseClient`/transaction boundary provide a migration seam, but a hosted PostgreSQL adapter, versioned production migrations, connection pooling, multi-instance session/rate-limit behavior, and operational backups must be verified before adding API replicas. Do not point multiple replicas at one embedded database directory.

First remove unbounded client reads and duplicated domain decisions. Use measured query/latency evidence before adding queues, services, or caches. Keep recommendation computation and catalog access behind existing service boundaries so scaling those workloads does not change client contracts. This goal will document remaining infrastructure limits without claiming load capacity that has not been measured.
